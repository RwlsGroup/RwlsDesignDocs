# Firmware Architecture

Embedded products in this documentation are organized around a bootloader and an application, with a separate BLE module firmware where present. Keep each image's responsibilities and upgrade boundaries explicit.

## Component boundaries

- **Bootloader:** startup checks, application handoff, and the update or recovery operations implemented by that target.
- **Application:** product workflows, user interface, sensor processing, and communication with peripherals and the BLE module.
- **BLE module firmware:** radio behavior, BLE services, and the module-side host interface. This is a separately versioned component when independently updated.

Some products combine or omit these components. The project overview is authoritative for which components are present.

Browse the focused pages for [peripherals](2.peripherals.md), [UART](2.peripherals.md), [I²C and its multiplexer](2.peripherals.md), [SPI/QSPI](2.peripherals.md), [OTA support](6.ota-support.md), [memory layout](6.ota-support.md), [external flash](6.ota-support.md), [update and recovery](6.ota-support.md), [pressure calculation and calibration](5.calculation.md), [display and input](3.display-and-input.md), [Bluetooth communication](4.bluetooth-communication.md), and [RS-232 communication](2.peripherals.md).

For each project, document the target part, toolchain, build configuration, memory layout, image format, boot sequence, version source, and compatibility requirements. For OTA, also document the transport, staging area, validation, activation, rollback/recovery behavior, and user-visible status.

Do not assume that a host application's OTA capability also updates the BLE module. Treat each independently updated image as a separate versioned component and identify compatible combinations.


# Shared Build and Release Practices

Use a repeatable build pipeline for each embedded project. Keep project-specific workflow files, tool versions, secrets, and triggers in that project's repository documentation.

## Build stages

1. Check out the intended source revision and its pinned dependencies.
2. Select the target, build configuration, and toolchain explicitly.
3. Build each independently versioned firmware component.
4. Validate that expected images exist and are non-empty; record the source commit and version.
5. Package the outputs in the formats required for factory programming and field updates.
6. Publish artifacts with clear names, retention, access controls, and traceability to the source revision.

## Release controls

- Validate release tags and embedded image versions before publishing.
- Sign update images when the product's update design requires a signature; protect signing keys as secrets.
- Keep development, test, pre-release, and production artifacts distinguishable.
- Publish checksums or provenance when required by the product release process.
- Notify the team with links to the completed build, release notes, and artifacts.
- Document rollback, recovery, and artifact retention policies per product.
